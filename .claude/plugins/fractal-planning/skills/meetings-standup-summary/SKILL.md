# Meetings · Standup Summary

You transform a raw standup meeting transcript (typically auto-generated by a meeting recorder) into a chat-ready markdown digest. The output is succinct, scannable, and pasted directly into a team chat channel — not a stored artifact.

**Design principle:** A teammate skimming the digest in 30 seconds should know (1) what each person is doing today, (2) where the team is blocked, and (3) where to find the source if they want more.

---

## Step 0 — Inputs

Required:
- **Transcript path** — path to a `.md` file containing a transcribed standup.

Optional (recommended — ask if not provided):
- **Video URL** — link to the cloud recording.
- **Doc URL** — link to the editable transcript document.

If invoked with arguments, parse them. If invoked bare (`/meetings-standup-summary`), ask the user for the transcript path and the two URLs in a single `AskUserQuestion` call.

---

## Step 1 — Read the Transcript

Read the entire file with the `Read` tool. Do not skim — auto-transcripts mangle proper nouns, project codenames, and short verbal name forms, so every line is potential context for disambiguation.

Build an internal model of:
- **Attendees** (usually listed at the top under `# Attendees` or `## Attendees`)
- **Speaker turns** — who said what, in roughly what order
- **Mentioned third parties** — people referenced but not present ("Ro said…", "the SRE recommended…")
- **Project / system names** — anything that looks like a codename, repo, branch, or tool
- **Action items, follow-ups, and blockers** flagged by anyone

---

## Step 2 — Disambiguation Pass (BEFORE writing anything)

This is the single most important step. **Do not skip it.** A skipped pass produces confident, wrong output — the classic failure is inventing a teammate out of a mistranscribed name and putting them in the digest.

> **Shared glossary:** before asking the user, consult the maintained codename and
> mistranscription glossary at `wiki/entities/glossary.md` (repo-relative). It holds confirmed
> mappings grouped by proper nouns, tools/vendors, acronyms, and people/roster. Apply those
> mappings silently — only ask the user about terms not covered there, or where transcript
> context contradicts a glossary row.
>
> The categories table below is the **fallback** when no glossary exists. The shared glossary is
> authoritative and grows over time.

Scan the transcript for these classes of ambiguity and collect them into ONE batched `AskUserQuestion` call (multi-question, single tool invocation):

### Categories to flag

| Category | What to look for | Why it matters |
|----------|------------------|----------------|
| **Garbled proper nouns** | Anything that sounds like a phonetic mangling of a real project, repo, branch, or service name | A wrong codename in the digest erodes trust and confuses readers |
| **Shortened verbal names** | A one-syllable form of an attendee's name, or a nickname | Could be a real teammate or a verbal shortening of someone already present — never assume |
| **Unknown people** | Any name not in the attendee list | Confirm the person actually exists on the team; do not invent teammates |
| **Tool / vendor names** | Partial or mis-cased product names, registries, CLI tools | Keeping them verbatim confuses the reader; guessing wrong misinforms them |
| **Acronyms & customer codes** | Two- and three-letter forms, references to customer projects | Could be a feature, a customer, or a service |
| **Ambiguous PR / ticket refs** | "PR1" vs "PR11", "the ticket" with no number | A wrong number sends reviewers to the wrong place |

### How to ask

Use a single `AskUserQuestion` call with up to 4 questions. Each question:
- Lists 2-3 candidate interpretations (mark one Recommended when you have strong evidence)
- Includes "Leave as-is (verbatim)" as a safety option
- Names the speaker context so the user can disambiguate from memory

**Roster check is mandatory.** If ANY name in the transcript is not in the attendee list, ask a question to confirm whether that person is a real teammate. Do not assume.

If ambiguity remains after the answers, ask a second round — but keep total rounds ≤ 2 to avoid stalling.

## Step 3 — Generate the Digest

Output format (paste-ready for team chat — most clients process GFM-flavored markdown and emoji shortcodes; substitute literal emoji if the target client does not):

```markdown
## Standup Digest — YYYY-MM-DD

**[Participant Name]**
- **Yesterday:** [1-3 sentences. Concrete actions completed. Translate codenames. Put any traffic-light emoji on the specific sub-task it relates to.]
- **Today:** [1-3 sentences. Concrete actions planned. Traffic-light emoji inline on the specific sub-task it relates to.]
- **Blockers:** [One line. If blocked, lead with `:red_circle:`. If FYI-only, lead with `:yellow_circle:`. If none, write "None."]

**[Next Participant]**
- ...

---

**Sources:**
- :movie_camera: [Video recording](<video URL>)
- :page_facing_up: [Full transcript](<doc URL>)
- :robot: processed via Claude Code by @**<your name>**
```

### Traffic-light rules (inline, not header-level)

- `:red_circle:` — **Blocked.** Work cannot proceed without external action (waiting on a person, infra, access).
- `:yellow_circle:` — **Warning / FYI.** Not blocked, but the team should know (slipped scope, unstable environment, missed dependency).
- `:green_circle:` — **Approval / unblocked.** A previously flagged item is now resolved or signed off.

**Critical:** place the emoji on the *specific task or blocker line* it modifies — not on the participant's name header. Scannability comes from seeing which exact item needs attention. A participant with no flags gets no emoji on their name at all.

### Content rules

- **Translate, don't transcribe.** Replace each mangled term with its canonical form using the answers from Step 2.
- **Use code formatting** for repo names, branches, registries, and CLI tools.
- **Bold key facts** in the body — environment-not-stable, demo-not-ready, deadline-relevant items.
- **Resolve relative time** to dates ("Friday" → `2026-08-21` if the meeting was Monday `2026-08-24`). Anchor on today's date from system context.
- **Don't pad.** If a participant spoke two lines, their summary is two lines. No filler.
- **Don't editorialize.** Do not add status colors that were not expressed, explicitly or strongly implied, in the transcript.

### Sources block

- Always include the video and document links if provided.
- **Do NOT** include the local `.md` file path. The raw file is a processing artifact; readers get the canonical shared links only.
- Always end with the robot signoff so readers know the digest is AI-generated:
  `:robot: processed via Claude Code by @**<inferred user name>**`
  (Use the git user or a memory-derived name. If unknown, ask before generating.)

## Step 4 — Output (chat) + Graduate (disk)

**4a — Print to chat.** Print the digest **directly to the chat** as your final response so the user can paste it into the team channel. This is the primary deliverable.

**4b — Graduate the meeting to the project meetings home.** Standup transcripts and summaries are project artifacts. If the repo has a meetings tree — `projects/<project>/meetings/active/{YYYYMMDD}/` is the convention; follow that tree's own README when one exists — then after printing the digest:

1. **Create** `projects/<project>/meetings/active/{YYYYMMDD}/` using the **meeting** date, not today's.
2. **Move the transcript** into it as `{date}-standup-transcript.md` — the immutable source of truth. The raw is never edited; disambiguation lives in the summary. If the transcript came from an inbox or a raw wiki tier, move it rather than copying, so there is exactly one home.
3. **Write the summary** as `MEETING-SUMMARY-{date}-standup.md` with frontmatter carrying `source:` (the transcript filename) and `source_hash:` (first 16 chars of its sha256), per the reprocess-on-edit convention. The body is the digest you printed, plus any discussion or ticket-mapping sections.
4. **Append a `graduate` row** to `wiki/log.md` and fix any inbound cross-links to the old paths.

If the repo has no meetings tree, fall back to chat-only and tell the user where you would have graduated it.

Do not commit. Do not edit the raw transcript's content. Re-indexing the wiki is a separate maintenance step — note it as pending rather than running it inline.

Built on the synthetic TaskFlow / NOVA fixture cast (`fixtures/taskflow/people.yaml`) — AR Alex Rivera, RV Rowan Vance, SP Sam Park, TN Toni Nguyen, CL Casey Lume. Fictional, illustrative only.

**Transcription artifacts the disambiguation pass should catch:**

| Heard in transcript | Real meaning | How we know |
|--------------------|--------------|-------------|
| "merge loom" / "merge bloom" | `mergeloom` (the CRDT library) | Codename consistency; recurs across speakers |
| "drift set branch" | the `driftset` evaluation branch | Phonetic mangling; only resolvable via the user |
| "nova dev" | a deployment environment, not a branch | Speaker context |
| "weave line" | `weaveline` (rejected candidate library) | Appears in the evaluation table |
| "Ro" | Rowan Vance (shortened verbal name) | Attendee list |
| "Casey" (mentioned, not present) | Real teammate — confirm before including | Roster check |

**Inline traffic-light placement (correct):**

```
- **Blockers:** :red_circle: Out of disk on the staging box — needs CL to expand storage.
```

**Header placement (incorrect — do not do this):**

```
**Rowan Vance** :red_circle:
- **Blockers:** Out of disk on the staging box...
```

The header version forces the reader to re-read the whole block to find what is red. Inline placement lets the eye jump straight to the actionable item.

## Gotchas

- **The disambiguation pass is the whole skill.** Skipping it to save a round-trip is how a fictional teammate ends up in a team channel.
- **One batched question, not six.** Six sequential `AskUserQuestion` calls will exhaust the user's patience before the digest exists.
- **The raw transcript is immutable.** Corrections live in the summary, never inline in the raw.
- **Emoji placement is load-bearing**, not decoration — see the correct/incorrect pair above.

## Reminder: What You Are NOT Doing

- You are not transcribing — the transcript already exists; you are digesting it.
- You are not interpreting tone or assigning blame — stick to what was said.
- You are not assuming team membership — any name not in the attendee list is a question, not a fact.
- You are not editing the raw transcript — graduate it verbatim; disambiguation lives in the summary (Step 4b). The chat digest is still the primary deliverable; the disk copy is the project record.
- You are not skipping the disambiguation pass to save time — it is the highest-leverage step in this skill.
