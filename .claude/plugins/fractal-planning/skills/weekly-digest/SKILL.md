# weekly-digest — multi-player team heartbeat

You are the **planning assistant**. Your job: scan the shared knowledge base over a date
window and produce a chat-ready digest that answers "what changed and what needs attention."
This is the **multi-player heartbeat** — surfacing presence, provenance, and active locks
that optimistic git alone does not surface.

**Design principle:** A teammate skimming in 60 seconds should know (1) what new knowledge
was filed, (2) what decisions moved, (3) what is open or blocked, and (4) whether anything
requires their attention.

## Inputs

- `--from` / `--to` date range (ISO 8601). Default: last 7 calendar days ending today.
- `--project` filter (optional): limit the decision-log scan to a specific project slug.
  Default: every decision-log directory the repo exposes.

If invoked bare (`/weekly-digest`), use defaults. If invoked with arguments, parse them.

## Path resolution (do this first)

The three input surfaces are conventions, not fixed paths. Resolve them once, up front, and
state what you resolved in the footer:

| Surface | Resolution order |
|---------|------------------|
| Wiki operation log | `wiki/log.md`, else the `log.md` under the vault root the repo's wiki index names |
| Decision log | `projects/*/decision-log/`, else `decision-log/` at the repo root, else the store path the user passes |
| Inbox | `_INBOX/` at the repo root, if one exists |

If a surface does not exist, say so in that section rather than silently omitting it. In this
repo the synthetic corpus at `fixtures/taskflow/` carries all three shapes and is a valid
target for a dry run (`--project taskflow` style invocation against
`fixtures/taskflow/wiki/log.md` and `fixtures/taskflow/decision-log/`).

Paste-ready chat markdown (GFM-flavored). Print directly to chat — do NOT write to a file
unless the user explicitly requests it.

## Steps

### Step 1 — Resolve date window

```python
from datetime import date, timedelta
today = date.today()
from_date = today - timedelta(days=7)   # override with --from arg if provided
to_date = today                          # override with --to arg if provided
```

### Step 2 — Read the wiki operation log

Read the resolved `log.md`. Filter rows where the date column falls within
[from_date, to_date]. Collect: date, operation, source/target, summary. Only `ingest` and
`synthesis` operations are relevant for the "New Sources" section.

### Step 3 — Scan decision-log entries

For each resolved decision-log directory (or the one named by `--project`):

```bash
python3 tools/decision-ledger/storage/cli.py --store <decision-log-path> list
```

Filter entries whose `updated` frontmatter timestamp falls within [from_date, to_date].
Collect: id, title, status, updated_by, updated.

Also collect every entry with status `open`, `in_discovery`, or `conflicted` for the
"Open Items" section regardless of date — those always need attention.

### Step 4 — Check for active locks

```bash
python3 tools/decision-ledger/storage/cli.py --store <decision-log-path> audit
```

Parse the audit output for locks that were never released. A lock older than 5 minutes with
no matching release is flagged as stale.

### Step 5 — Scan for unresolved candidate decisions

Read every `wiki/sources/*.md` modified within [from_date, to_date] (use `git log` or file
modification dates). Extract the `## Candidate Decisions` table rows from each.
Cross-reference against the decision log: a candidate whose exact title already appears as a
decision entry title counts as promoted and is omitted from the digest.

```bash
git log --since="YYYY-MM-DD" --until="YYYY-MM-DD" --name-only --pretty=format: \
  -- wiki/sources/ | grep "\.md$" | sort -u
```

### Step 5b — Check `_INBOX/` for unrouted items

```bash
find _INBOX/ -type f ! -name '.gitkeep' ! -name 'README.md' | wc -l
find _INBOX/ -type f ! -name '.gitkeep' ! -name 'README.md'
```

Collect the count and filenames for the "Unrouted `_INBOX` Items" section. If zero, emit
`*(Inbox clear.)*`. If there is no `_INBOX/`, say the repo has none.

### Step 6 — Build and print the digest

Assemble all sections. Rules:
- If a section has no items, include it with a `*(None this period.)*` note — do not
  silently omit sections; absences are informative.
- Round decision activity to the most recent update per entry (do not emit one row per
  update on the same entry inside the window).
- Sort entries by date descending within each section.
- No secrets, credentials, or personal data in the output.

### Step 7 — Print and done

Print the digest to chat. Do not commit anything. Do not write to disk unless the user
explicitly asks to save it.

- [ ] Resolved source paths stated in the footer

- [ ] Decision IDs are accurate (read from `dl list` output, never guessed)
- [ ] Candidate decisions cross-referenced against promoted entries (no duplicates)
- [ ] `_INBOX/` scanned; unrouted count reported (or "Inbox clear", or "no inbox in this repo")
- [ ] No secrets or personal data in any output
- [ ] Output ends with the promote-to-ledger call-to-action

## Constraints

- Read-only. This skill does not write, commit, or modify any file.
- Never guess at decision IDs or statuses — read them from the store.
- If `tools/decision-ledger/storage/cli.py` is not available, note the degraded state and
  emit the Sources and Candidates sections only — those come from markdown files.

## Gotchas

- **A missing surface is a reportable fact, not a silent skip.** A digest that omits the
  Decision Activity section because the store path was wrong reads exactly like a quiet week.
- **`updated` is frontmatter, not mtime.** Filtering on file modification time double-counts
  files touched by an index rebuild.
- **Locks are advisory and short.** A "stale lock" is usually an interrupted session, not a
  conflict — report it, do not break it.
